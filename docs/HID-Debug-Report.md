# VMware Fusion USB HID 直通：一次完整的排障与对照实验

> 记录日期：2026-11-06 ～ 2026-11-07  
> 环境：Apple Silicon Mac／VMware Fusion／Windows 11 ARM64  
> 状态：**发现并验证一次可行绕行方法；根因与跨环境可重复性尚未完全确定**。

## 1. 摘要

一只通过 USB 数据线连接、处于 Xbox／XInput 模式的 GameSir Nova 2 Lite 手柄，在 macOS 中可被检测到，也曾成功直通 Windows 11 ARM 虚拟机。但在后续拔插后，Fusion 拒绝将其连接到 Windows，并显示：

> `The host requires this device for input.`

我们曾尝试设置设备默认连接目标，也尝试增加 `.vmx` 参数 `usb.generic.allowLastHID = "TRUE"`（后者引发虚拟机配置报错，回滚后恢复）。最终在不放宽最后 HID 保护的情况下，通过**增加一只留在宿主机的 Rapoo 鼠标**成功建立手柄直通。此后**拔掉 Rapoo 鼠标，已直通的手柄仍能工作**。

这提示需要区分两种行为：① 新建 USB HID 直通连接时的准入判断；② 已建立 USB 直通连接后的保持与释放。但这仍是根据外部现象提出的机制假说，而非 VMware 源码层面的证明。

## 2. 初始目标与环境

本次排查最初是为了在 Apple Silicon Mac 上运行《湾岸5DX》，并让实体手柄的摇杆、按钮和扳机被 Windows／JConfig／游戏识别。

| 层级 | 已知信息 |
|---|---|
| macOS 宿主机 | Apple Silicon Mac，内置键盘及触控板可用 |
| 虚拟化 | VMware Fusion，确切版本／构建号尚未记录 |
| Windows 客体 | Windows 11 ARM64 |
| 手柄 | GameSir Nova 2 Lite（启明星2），USB 线缆，绿色 Xbox／XInput 模式 |
| 设备在 VMware 中的名称 | `2.4G XBOX 360 For Windows`（连接方式与该显示名称不一定一致） |
| 辅助输入设备 | Rapoo USB 鼠标，曾显示 `Shenzhen Rapoo Rapoo Gaming Device` |
| 游戏输入验证 | Windows `joy.cpl`、JConfig 1.8、游戏 Test Mode |

## 3. 排障时间线

### 阶段 A：手柄已经能够被系统识别

macOS 的 USB 设备视图中能够看到 Xbox 兼容手柄；此前通过 VMware USB 直通，Windows `joy.cpl` 曾显示 `Controller (XBOX 360 For Windows)`。我们在 JConfig 中使用 XInput，并完成过游戏内方向盘、油门、刹车输入测试。

因此后续的问题并非简单的“手柄根本不支持 Windows ARM”。

### 阶段 B：拔插后拒绝重新直通

手柄重新插入后，VMware Fusion 的 USB 设置显示该设备，但尝试交给 Windows 时出现：

> `The host requires this device for input.`

将默认连接规则设为 **Connect to this virtual machine**，未能解除该报错。这一结果表明问题不只是在自动连接偏好设置上。

### 阶段 C：`.vmx` 修改的失败与回滚

既有可启动的 `.vmx` 包含：

```ini
usb.generic.allowHID = "TRUE"
```

我们又尝试添加：

```ini
usb.generic.allowLastHID = "TRUE"
```

添加后虚拟机报 `VMX file is corrupt`，**删除新加行后重新正常启动**。随后对文件进行了只读格式检查：非 RTF、未发现异常格式行、弯引号或 UTF-8 解码错误。

这一对照足以让我们**停止继续冒险修改可工作的配置**；但仅凭它不能确定具体损坏原因，亦不能推断官方参数普遍不兼容。此前部分排查过度关注文件语法，忽略了“添加 → 失败 → 回滚 → 恢复”的直接因果线索。

### 阶段 D：追加一只留给 macOS 的外接鼠标

在 Mac 上连接 Rapoo USB 鼠标，保持该鼠标归 **macOS 宿主机**使用，然后把 Xbox 兼容手柄连接到 Windows。

**结果：手柄直通成功。**

当手柄已经在 Windows 内工作时，尝试将 Rapoo 鼠标也直通给 Windows，则受到保护性限制。这与宿主机输入设备保护的设计目的相吻合。

### 阶段 E：移除临时辅助设备

**在手柄已成功直通后，将 Rapoo 鼠标物理拔掉。**

**结果：手柄继续在 Windows 中正常使用；MacBook 的内置键盘和触控板也正常。**

这个现象是本次排障的最重要补充：**辅助输入设备可能在建立连接时有用，但保持既有直通连接并不要求它持续插着。**

## 4. 实验矩阵

| 编号 | 条件／操作 | 实测结果 | 证据意义 |
|---|---|---|---|
| T1 | 手柄单独连接，尝试直通 | 失败，显示 Host requires device | 确认保护性拦截症状 |
| T2 | 设置默认连接目标为 Windows | 仍失败 | 默认连接规则不能解决该次拦截 |
| T3 | 在 `.vmx` 增加 `allowLastHID` | `VMX file is corrupt` | 说明该变更与启动失败关联，不证明参数本身错误 |
| T4 | 删除该新增行 | 恢复正常启动 | 回滚验证 |
| T5 | 加入 Rapoo 鼠标并留在 macOS，再直通手柄 | 成功 | 额外宿主机输入设备改变了连接结果 |
| T6 | 手柄已直通时尝试将 Rapoo 鼠标也直通 | 被限制 | 与宿主机 HID 保护假说一致 |
| T7 | 保持手柄连接 Windows，拔掉 Rapoo 鼠标 | 手柄和 Mac 内置输入均正常 | 已建立直通未因辅助鼠标移除而立即撤销 |

> **证据强度**：T1～T7 是用户本机实际观察；尚未在不同设备、不同版本、多次重复冷启动以及新的热插拔循环中系统性复现。不能据此计算普适成功率。

## 5. 机制分析：事实、推测、未知

**已知事实**：

- 报错明确包含 `The host requires this device for input`。
- 加入留给 macOS 的外接鼠标后，手柄可以直通；把该鼠标也移交 Windows 受到限制。
- 移除辅助鼠标后，既有手柄连接保持正常。
- 内置键盘和触控板在最终状态中可以使用。

**与事实一致的解释**：Fusion 的 HID 宿主机保护参与连接准入，但对已建立连接未必持续进行相同的判断，或者至少不会在移除辅助鼠标时立即撤销手柄连接。

**我们不能声称已经证明**：

- Fusion 内部一定按 HID 数量（如“两台才允许一台直通”）进行简单计数；
- MacBook 内置键盘与触控板是否被该保护逻辑识别，以及它们被如何分类；
- 所有外接鼠标、所有接口、所有 Fusion 版本都能复现；
- 这是 VMware 安全漏洞、权限绕过漏洞或新的软件 Bug；
- `allowHID` 不必要、`allowLastHID` 参数有设计错误。

**官方背景**：Broadcom 知识库文章 344342 介绍了 Fusion 对鼠标／键盘等 USB HID 的直通保护，并说明 `usb.generic.allowHID` 与可选 `usb.generic.allowLastHID` 的作用。该文章最初覆盖的 Fusion 版本与本机当前环境未必完全一致，因此不能把官方配置视为本机必然有效的保证。

参考：https://knowledge.broadcom.com/external/article/344342

## 6. 目前推荐的操作步骤

仅当你的症状与本报告相同、并且 **Mac 自身仍有可靠输入方式** 时尝试：

1. 先保持已经能够启动的虚拟机配置，关闭任何会自动把鼠标也直通进客体的规则。
2. 将备用 USB 鼠标连接到 macOS，确认其**留在宿主机**。
3. 把 Xbox 兼容手柄连接至 Mac，在 Fusion USB 菜单中将手柄连接到 Windows。
4. 在 Windows `joy.cpl` 验证手柄按钮、摇杆、扳机。
5. 如需拔掉备用鼠标，先确认 MacBook 内置键盘和触控板可用，再观察手柄连接是否保持；不保证在其他机器也适用。
6. 如果失败，恢复原设备状态，不要为了复现而强制直通最后一个可用键盘或鼠标。

**不要将“屏蔽保护”作为默认方案**。强制直通宿主机最后一个可用输入设备可能导致暂时无法操作 Mac。

## 7. 后续实验建议

在备份及可恢复环境中，按优先级补充：

1. 记录精确的 VMware Fusion 版本／构建号、macOS 版本、手柄 VID/PID、Hub／USB 接口情况。
2. 重复一次“只有手柄 → 失败 → 插入鼠标 → 成功 → 拔掉鼠标仍成功”的完整流程，确认可重复性。
3. 分别测试不同 USB 端口与不同备用输入设备，验证是否存在设备类别差异。
4. 在不修改虚拟机配置的情况下，分析 `vmware.log` 中设备枚举及直通拒绝事件，区分连接错误与 HID 宿主机保护。
5. 如需深入研究 `allowLastHID` 导致的启动错误，**在复制的测试虚拟机**中进行，并仅比较最小改动；不要再用可工作的正式 Windows 环境冒险。

## 8. 结论

本次记录的成果是一个**经过实际操作验证的 HID 直通绕行办法**，以及一个值得进一步验证的机制假说：**建立连接的准入检查和既有连接的保持可能采用不同条件**。

最重要的工程教训不是“找到神奇配置项”，而是通过对照实验识别问题边界、及时回滚引发故障的变更，并明确区分“实验结果”和“机制推断”。
